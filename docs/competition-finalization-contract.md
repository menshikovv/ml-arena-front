# Подведение итогов: требования к backend

Ниже сохранено исходное предложение контракта. По отчёту backend-разработчика переход
финализации реализован. Backend в рамках frontend-задачи не изменялся.

Frontend подключает `POST /finalize` с обязательной причиной и обновляет данные с сервера
перед дальнейшей публикацией. Публикация остаётся отдельной операцией `reveal-private`.
Кнопка начала доступна после дедлайна для `active` / `paused`, с правом `leaderboards.reveal`.
Двойной запрос блокируется до завершения операции и обновления данных.

Контракт из `answer.md` подключён: frontend запрашивает `/publication-readiness`,
показывает весь массив блокировок, число допущенных/исключённых участников и закрывает
публикацию при отсутствии явного `publication_ready: true`. Перед reveal готовность
проверяется ещё раз. Окончательное решение всегда принимает backend.

В редактор добавлены `source_code_required` и `source_code_deadline`. Неизменённая
политика не отправляется повторно; зафиксированные настройки недоступны для изменения.
Legacy `final_results_at` больше не отправляется как редактируемая плановая дата.
Архив проверяется через private leaderboard и `private_locked === false`, а не по
дате или служебному снимку. Скрытые private-score в отправках архива не отображаются.

Локальная копия backend пока не содержит новой реализации. Проверки frontend выполнены
с изолированными ответами по контракту; сквозной прогон с обновлённым API ещё нужен.

## Исходная проблема

- После `submission_deadline` соревнование остаётся в серверном статусе `active`.
- Frontend показывает «Приём завершён», но не меняет серверный статус.
- Существующий `POST /api/v1/admin/competitions/{id}/leaderboard/reveal-private`
  принимает `{ "reason": "Проверка решений завершена" }`, требует право
  `leaderboards.reveal` и допускает только `finalizing` / `completed`.
- В проверенном backend отсутствует переход `active -> finalizing`.
- Архивирование и перенос дедлайна не должны использоваться как обход публикации итогов.

## 1. Начать финализацию

Предлагаемый endpoint: `POST /api/v1/admin/competitions/{id}/finalize`.

Авторизация: Bearer; право `leaderboards.reveal` (уже используется для публикации).
Тело: `{ "reason": "Приём завершён, начинаем финальную проверку" }`.
Причина обязательна: 3–1000 символов после обрезки пробелов.

Сервер должен атомарно:

1. Проверить права и доступ к указанному соревнованию.
2. Проверить серверное время: `submission_deadline` (либо канонический legacy `deadline`)
   должен наступить. До дедлайна вернуть `409 competition_deadline_not_reached`.
3. Разрешить переход только из `active` / `paused` в `finalizing`.
   Повторный запрос для `finalizing` идемпотентен и не создаёт повторных задач.
   Для черновика, архива и завершённого соревнования вернуть `409 invalid_competition_state`.
4. Сохранить причину и администратора в журнале аудита.
5. Остановить новые отправки. Не открывать приватные оценки на этом шаге.

Ответ `200`: `{ "data": { "id": "UUID", "status": "finalizing" }, "meta": { "request_id": "..." } }`.
Остальные поля могут соответствовать существующему объекту соревнования.
Если нужен асинхронный пересчёт, необходимо отдельно согласовать `202`, job ID и endpoint статуса.

## 2. Опубликовать итоги

Сохранить существующий `POST /api/v1/admin/competitions/{id}/leaderboard/reveal-private`
с обязательным `reason` и серверной проверкой `leaderboards.reveal`.

Перед публикацией сервер проверяет:

- Соревнование находится в `finalizing`; не осталось незавершённых проверок/пересчётов.
- Закрыто отдельное окно загрузки итогового кода, если оно предусмотрено правилами.
- Для итогового рейтинга применены серверные правила допуска. По требованию продукта
  участник без обязательного итогового кода исключается из приватного рейтинга,
  но остаётся в публичном. Проверяются владелец, `submission_id`, purpose и готовность файла.
- Места, число допущенных участников и сезонные очки рассчитаны после применения допуска.

Публикация должна согласованно зафиксировать приватный снимок, `completed`, фактическое
`final_results_at` и сезонный рейтинг. Ошибка не должна оставлять частично опубликованные итоги.
Повторы/конкурентные запросы не должны повторно начислять очки.
Поведение повторной публикации из `completed` нужно сохранить совместимым либо явно согласовать.

После успешной публикации:

- GET соревнования возвращает `status: completed`.
- GET приватного лидерборда возвращает `kind: private`, `private_locked: false` и итоговые строки.
- До публикации приватные оценки остаются недоступны обычному участнику независимо от дедлайна.
- ML-паспорт и карточка результата используют тот же опубликованный итог и правила допуска.

## Ошибки и проверки

Не использовать стартовую проверку `deadline > now` как условие публикации: после приёма
истёкший дедлайн ожидаем. Для этапа итогов нужны отдельные признаки готовности и причины
блокировки (например, `publication_ready` и `publication_blockers` в административном ответе).
Они не заменяют повторную проверку условий сервером в самом запросе публикации.

Вернуть стабильные коды ошибок (помимо HTTP), например `finalization_in_progress`,
`source_code_window_open`, `invalid_competition_state`; сообщения должны быть пригодны для локализации.
Проверить: отсутствие прав, ранний запрос, истёкший дедлайн, повтор/конкурентные запросы,
незавершённые пересчёты, код отсутствует/чужой/не привязан/не готов, ошибка транзакции,
успешная публикация и отсутствие утечки приватной оценки до неё.

## Подключение frontend

После реализации и подтверждения контракта добавить кнопку «Начать финализацию» для закрытого
приёма, затем использовать существующую «Опубликовать итоги». Во время пересчёта показывать
реальное серверное состояние. После операций обновлять соревнование, админский список,
лидерборды и карточку результата. Не вычислять факт публикации из одного лишь времени дедлайна.
