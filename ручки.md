### 1.1 Что такое бейджи и откуда они берутся

Бейдж — подтвержденное достижение пользователя, отображаемое в ML-паспорте.
Например: «Первый валидный submit», «Первая победа», «10 дуэлей»,
«Победитель соревнования», «Gladiator of the Week», «Premium».

Нужны две сущности:

- `badge_definitions` — справочник типов бейджей. Создается миграциями/seed-ами
  и управляется администратором.
- `user_badges` — факт выдачи конкретного бейджа конкретному пользователю.

Обычный пользователь не может выдать бейдж себе. Большинство бейджей выдает
backend автоматически после доменных событий. Ручная выдача и отзыв доступны
только администратору и записываются в audit log.

### 1.2 Кто может отправлять приглашения на работу и нужна ли ручка

Ручка нужна. Email — только канал уведомления, а приглашение должно:

- храниться в кабинете компании и у кандидата;
- иметь статусы `sent/viewed/accepted/declined/expired/withdrawn`;
- быть доступным для аудита и защиты от спама;
- не теряться при проблемах с почтой.

Отправитель — не обычный пользователь и не обязательно администратор платформы.
Это участник подтвержденной организации с ролью `owner`, `manager` или
`recruiter`. Кандидат должен заранее включить `visible_to_employers`.
Frontend отправляет `candidate_user_id`, вакансию и текст. Название компании,
email кандидата и отправителя backend берет из БД, а не доверяет frontend.

### 1.3 Что такое upload

Публичной универсальной ручки, которая принимает любой файл и возвращает
постоянный URL, быть не должно. Используется безопасная двухэтапная загрузка:

1. Frontend запрашивает временный upload URL и указывает назначение файла.
2. Frontend загружает файл напрямую в S3-совместимое хранилище.
3. Frontend передает `upload_id` в доменную ручку: submit соревнования,
   submit дуэли, аватар, датасет и т. п.
4. Backend проверяет владельца, назначение, размер, MIME, checksum и результат
   антивирусной проверки.

Скачивание приватных файлов выполняется только по короткоживущим signed URL.

### 1.4 Что такое send-email

Публичной ручки `/send-email` для frontend быть не должно. Иначе клиент сможет
рассылать письма от имени платформы.

Backend сам ставит транзакционные письма в очередь после событий:

- подтверждение email и сброс пароля;
- приглашение на работу;
- приглашение на дуэль и результат дуэли;
- завершение scoring submit-а;
- важное изменение соревнования;
- оплата, отмена и окончание Premium.

Для тестирования шаблона допустима отдельная admin-only ручка, но не
пользовательская интеграция.

### 1.5 Откуда берутся тарифы

Источник истины — таблица `billing_plans`, заполненная seed-миграцией и связанная
с `product_id/price_id` Stripe. Frontend получает только
опубликованные активные планы.

Для MVP:

- `free` — бесплатный базовый доступ;
- `premium_monthly` — `690 RUB / month`;
- `compare_at_amount` для интерфейса — `990 RUB`.

Удалять использованный план нельзя: его можно архивировать. Полноценный CRUD
тарифов в первой версии не обязателен. Достаточно seed + admin update/publish.
Цена, валюта и entitlement-ы не принимаются от frontend при оплате.

Premium не меняет score, лимиты rated submit-ов, Elo, matchmaking или
HR-ранжирование. Это обязательное бизнес-правило.

## 2. Архитектурные правила

### 2.1 Компоненты backend

- REST API — команды и чтение данных.
- PostgreSQL — пользователи, соревнования, дуэли, платежи, статусы.
- Redis — rate limit, matchmaking, presence, короткие блокировки.
- Object storage — CSV, датасеты, аватары, логотипы, артефакты.
- Job queue/worker — валидация CSV, scoring, агрегации, email, генерация данных.
- WebSocket или SSE — дуэли, уведомления, прогресс submit-а.
- Stripe — Checkout, Customer Portal и webhook-и.

### 2.2 Что frontend не имеет права определять

Backend игнорирует или отклоняет присланные клиентом:

- `role`, `organization_id` вне разрешенного контекста membership;
- `score`, `public_score`, `private_score`;
- `rating`, `elo`, `rating_change`, `rank`, `winner_user_id`;
- `subscription_status`, `is_premium`, цену и валюту;
- `submission.status`, `duel.status`, `competition.status` без разрешенной команды;
- `verified`, `trust_level`, `badge_id` для самостоятельной выдачи;
- email другого пользователя и произвольный адрес получателя платформенного письма;
- постоянный `file_url` вместо выданного backend `upload_id`.

### 2.3 Идентификаторы и деньги

- Идентификаторы — UUID/ULID, непрозрачные для frontend.
- Деньги — целое число в минимальных единицах: `69000` копеек.
- Валюта — ISO 4217: `RUB`.
- Числа score хранятся как decimal, не как строка с `%`.
- Форматирование score в UI выполняется по `metric.direction` и
  `metric.display_format`.

### 2.4 Удаление

Для бизнес-сущностей используется archive/soft delete. Физическое удаление
допустимо только для временных файлов после retention period и для персональных
данных в рамках законного запроса пользователя.

## 3. Роли и доступ

### 3.1 Системные роли

| Роль | Возможности |
|---|---|
| `anonymous` | Лендинг, опубликованные соревнования, публичный leaderboard, планы |
| `user` | Профиль, участие, submit-ы, дуэли, Premium, ответы на job invite |
| `moderator` | Модерация обсуждений, жалоб и публичного контента |
| `admin` | Управление платформой, пользователями, справочниками, аудит |
| `service` | Только internal API для worker-ов, не выдается frontend |

### 3.2 Роли внутри организации

| Роль membership | Возможности |
|---|---|
| `owner` | Все действия организации, участники, биллинг компании |
| `manager` | Соревнования, кандидаты, приглашения |
| `recruiter` | Поиск видимых кандидатов, job invite, HR-воронка |
| `viewer` | Только просмотр разрешенных данных организации |

Один пользователь может быть `user` платформы и одновременно иметь membership
в одной или нескольких организациях.

### 3.3 Обязательные проверки доступа

- Любой write endpoint требует аутентификацию.
- Доступ к организации проверяется по membership в БД на каждом запросе.
- Доступ к submit-у — владелец, организатор соответствующего соревнования или
  admin; организатор не видит скрытые данные, способные нарушить честность, до
  разрешенного этапа.
- В дуэли приватные данные видят только два участника и admin по audit-причине.
- Публичный ML-паспорт не содержит email и закрытые карьерные контакты.
- Поиск кандидатов возвращает только `visible_to_employers=true`.
- Private leaderboard недоступен участникам до финализации соревнования.

## 4. Аутентификация и сессии

Рекомендуемая схема:

- access token: JWT, срок 10–15 минут, передается в
  `Authorization: Bearer <token>`;
- refresh token: случайный opaque token в `HttpOnly; Secure; SameSite=Lax`
  cookie, хранится в БД в хешированном виде;
- refresh token rotation при каждом обновлении;
- отзыв всех сессий при смене пароля;
- email должен быть подтвержден до submit-а, дуэли и действий компании.

Если и access token хранится в cookie, для всех изменяющих запросов требуется
CSRF token.

### POST `/auth/register`

Доступ: `anonymous`.

```json
{
  "email": "user@example.com",
  "password": "long-password",
  "username": "datawizard",
  "accepted_terms": true,
  "accepted_privacy": true
}
```

Ответ `201`:

```json
{
  "data": {
    "user": {
      "id": "usr_01",
      "email": "user@example.com",
      "email_verified": false,
      "role": "user"
    },
    "verification_required": true
  }
}
```

Ошибки: `EMAIL_ALREADY_EXISTS`, `USERNAME_ALREADY_EXISTS`,
`WEAK_PASSWORD`, `TERMS_NOT_ACCEPTED`.

### POST `/auth/login`

Доступ: `anonymous`. Rate limit обязателен.

```json
{
  "email": "user@example.com",
  "password": "long-password"
}
```

Ответ `200`: access token, пользователь и список membership-ов. Refresh token
устанавливается cookie.

### POST `/auth/refresh`

Доступ: валидный refresh cookie. Возвращает новый access token и ротирует
refresh token.

### POST `/auth/logout`

Отзывает текущую refresh-сессию и очищает cookie.

### POST `/auth/logout-all`

Отзывает все сессии текущего пользователя.

### GET `/auth/me`

Возвращает пользователя, permissions, membership-ы и краткое состояние
подписки.

```json
{
  "data": {
    "id": "usr_01",
    "email": "user@example.com",
    "email_verified": true,
    "role": "user",
    "permissions": ["competition.submit", "duel.play"],
    "memberships": [
      {
        "organization_id": "org_01",
        "organization_name": "T-Bank",
        "role": "recruiter"
      }
    ],
    "subscription": {
      "plan_code": "premium_monthly",
      "status": "active",
      "current_period_end": "2026-08-30T00:00:00Z"
    }
  }
}
```

### POST `/auth/email/verify/request`

Повторно ставит письмо подтверждения в очередь. Ответ всегда нейтральный.

### POST `/auth/email/verify/confirm`

```json
{ "token": "single-use-token" }
```

### POST `/auth/password/forgot`

```json
{ "email": "user@example.com" }
```

Всегда `202`, независимо от наличия email, чтобы не раскрывать пользователей.

### POST `/auth/password/reset`

```json
{
  "token": "single-use-token",
  "new_password": "new-long-password"
}
```

После успеха отзываются все старые сессии.

## 5. Общий формат API

### 5.1 Успешный ответ

```json
{
  "data": {},
  "meta": {
    "request_id": "req_01"
  }
}
```

### 5.2 Список с cursor-пагинацией

Запрос:

`GET /competitions?limit=20&cursor=opaque_cursor`

Ответ:

```json
{
  "data": [],
  "meta": {
    "next_cursor": "opaque_next_cursor",
    "has_more": true,
    "total": 124,
    "request_id": "req_01"
  }
}
```

`limit`: по умолчанию 20, максимум 100. Cursor непрозрачен.

### 5.3 Ошибка

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Некоторые поля заполнены неверно",
    "field_errors": {
      "filename": ["Разрешены только CSV-файлы"]
    },
    "retry_after_seconds": null,
    "request_id": "req_01"
  }
}
```

Основные HTTP-коды:

- `400` — неверный формат команды;
- `401` — не авторизован;
- `403` — нет доступа;
- `404` — сущность не найдена или скрыта политикой доступа;
- `409` — конфликт состояния/повторное действие;
- `413` — файл слишком большой;
- `422` — доменная валидация;
- `429` — rate limit;
- `500` — внутренняя ошибка без технических деталей;
- `503` — временно недоступен worker/провайдер.

### 5.4 Идемпотентность

Для создания submit-а, job invite, checkout session, challenge и admin-команд
frontend передает `Idempotency-Key`. Повтор команды с тем же ключом и телом
возвращает тот же результат. Тот же ключ с другим телом дает `409`.

### 5.5 Конкурентные изменения

Объекты с редактированием имеют `version`. Для PATCH frontend передает
`If-Match: "<version>"`. При устаревшей версии — `409 VERSION_CONFLICT`.

score curve и verification state. Private score показывается только после

Cursor-пагинация. Типы событий: join, dataset_download, valid_submission,

Публичные выданные бейджи. См. раздел 8.

Обычный пользователь: поиск публичных профилей по username.

- `DELETE /profiles/me/experience/{experience_id}`

Поля: `company`, `position`, `started_at`, `ended_at`, `is_current`,

- `POST /profiles/me/verifications/{id}/evidence` — привязать `upload_id`.
- Решение принимает admin через admin endpoint.

Типы: `identity`, `github`, `solution_reproducibility`, `education`.

## 10. Соревнования

### 10.1 Жизненный цикл

`draft -> moderation -> scheduled -> active -> finalizing -> completed -> archived`

- Организация создает draft.
- Publish проходит после валидации и при необходимости модерации.
- `scheduled`, `active`, `finalizing` и `completed` переключаются backend по

- Frontend не передает `active` при создании.

- `premium` — только активная Premium-подписка, но соревнование не должно

## 11. Дуэли

### 11.1 Правила доверия

- Backend выбирает задачу из активного пула по выбранному направлению.
- Оба игрока получают одинаковую версию данных.
- Score считается только worker-ом на скрытом target.
- Таймер рассчитывается по `server_time`, `started_at`, `ends_at`.
- Победитель и изменение Elo фиксируются одной DB-транзакцией.
- Frontend не может PATCH-ить score, winner или rating.

Основные статусы дуэли:

Дополнительные: `declined`, `cancelled`, `expired`, `void`.

## 19. Internal API и фоновые процессы

Эти endpoints не доступны frontend и защищены отдельным service credential,
mTLS/private network и allowlist.

### Scoring pipeline

1. API создает submission `uploaded`.
2. Validator проверяет upload, schema, row count, id uniqueness, NaN и порядок.
3. При успехе атомарно списывается попытка и создается scoring job.
4. Worker считает public score на закрытом target.
5. Backend сохраняет raw score, обновляет best submission и leaderboard.
6. После финала worker считает private score и final rank.
7. Rating/badges/profile aggregates обновляются идемпотентно.
8. Создаются notification и email job по настройкам.

Повтор worker job не должен второй раз списывать попытку, рейтинг или выдавать
бейдж.

### Email jobs

Внутренний service принимает только template key и domain entity id. Получатель,
locale и данные шаблона загружаются backend из БД.

Запрещено передавать из frontend произвольные HTML, sender и recipient.

### Планировщики

- переключение competition status;
- финальный scoring;
- истечение challenge/job invite/upload;
- отмена stale matchmaking ticket;
- billing entitlement reconciliation;
- пересчет materialized profile stats;
- удаление временных файлов.

## 21. Метрики и бизнес-правила

Справочник metric должен задавать:

```json
{
  "code": "roc_auc",
  "label": "ROC-AUC",
  "direction": "maximize",
  "display_format": "0.0000",
  "allowed_task_types": ["classification", "tabular"]
}
```

Минимум MVP: `rmse`, `mae`, `accuracy`, `f1`, `roc_auc`, `dice`.

Лиги:

- Bronze: `< 1100`;
- Silver: `1100–1299`;
- Gold: `1300–1499`;
- Platinum: `>= 1500`.

Границы должны жить в backend config/таблице seasons, а frontend получает
готовый league object. Изменение границ не должно требовать релиза frontend.

Для Elo:

- расчет только после валидного завершения rated duel;
- `void` не меняет рейтинг;
- изменение обоих игроков в одной транзакции;
- формула и K-factor версионируются;
- replay одного result event не начисляет Elo повторно.

## 23. Безопасность и приватность

Обязательно:

- TLS везде.
- Пароли Argon2id/bcrypt с актуальными параметрами.
- Секреты только в secret manager/env, не в frontend.
- Проверка authorization на объект, а не только role middleware.
- Параметризованные запросы/ORM, защита от SQL injection.
- Sanitize пользовательского markdown/URL.
- CSP, CORS только для разрешенных origin.
- Refresh rotation, session revocation, audit login events.
- Signed URLs с коротким TTL.
- Malware scan и content sniffing upload-ов.
- Webhook signature и replay protection.
- Ограничение размера JSON body и файла.
- Не логировать password, token, полный signed URL, payment data и содержимое
  приватного датасета.
- Request ID во всех логах и ответах.
- Маскирование PII в admin logs.
- Резервные копии и проверяемое восстановление.

Для честности ML-соревнований:

- target и private split никогда не выдаются клиенту;
- scoring image/config недоступны organizer после старта без audit;
- изменения dataset/metric версионируются;
- worker запускается изолированно с CPU/RAM/time limits;
- leaderboard и rating обновляются транзакционно;
- организатор не может посмотреть submissions пользователей произвольно, если
  правила не предусматривают проверку решения после завершения.

## 27. Definition of Done для каждой ручки

Ручка считается готовой, если:

- описаны request/response schema и enum-ы;
- есть schema validation;
- есть authentication и object-level authorization tests;
- есть happy path и негативные integration tests;
- ошибки имеют стабильный `error.code`;
- write operation пишет audit там, где это требуется;
- есть rate limit;
- есть idempotency для финансовых и создающих дубликаты операций;
- PII не попадает в чужой ответ и логи;
- OpenAPI обновлен;
- frontend может отличить loading/empty/error/forbidden/conflict states;
- асинхронная операция имеет status endpoint и не зависает без terminal state.

## 29. Рекомендуемый OpenAPI и порядок согласования

После согласования этого документа backend создает `openapi.yaml`. Для каждого
endpoint в OpenAPI должны быть:

- operation id;
- security scheme;
- request/response schema;
- все доменные error code;
- enum с описанием переходов;
- пагинация;
- примеры;
- rate-limit headers.

Сначала согласовать четыре наиболее рискованных sequence diagram:

1. Competition upload -> validation -> scoring -> leaderboard.
2. Duel matchmaking -> lobby -> live -> result -> Elo.
3. Job invite -> in-app notification -> email -> candidate response.
4. Checkout -> provider webhook -> entitlement.

Именно эти процессы нельзя надежно определить только набором CRUD-ручек.
